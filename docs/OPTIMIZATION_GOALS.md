# AI-TV-Butler V3 优化目标与验收任务书

> 本文是后续开发的目标与验收依据，不代表相关优化已经实现或通过测试。
> 基于当前项目源码及最近一次只读审查整理。当前源码版本为 3.0.0；历史“V3 已完整可部署”的结论需要以本任务书规定的实际验收重新确认。

## 1. 总体目标

将已有电视控制程序优化为能够日常稳定使用的 NAS 电视助手：用户说出自然语言目标后，系统能完整理解要求，以尽量少的模型请求和设备读取完成操作，准确反馈结果，并在异常时有界恢复或安全交还控制权。

本轮以“常用功能可用、执行速度、目标准确、反馈可信、部署可靠”为优先级，不以新增模块数量、版本号或单元测试数量作为完成标准。

必须达到以下结果：

1. 普通浏览器能够完成登录、发送任务、查看实时进度、控制任务和保存配置。
2. 打开应用、播放指定内容、暂停/继续、选集、跳转进度、返回和音量等常用操作有明确行为与核验方式。
3. 不丢弃片名、季集、附加动作、时间约束，不把查询当成播放。
4. 简单任务走轻量执行路径，复杂任务才使用完整观察与模型规划。
5. 恢复不仅记录“可以重试”，而且确实执行受预算约束的恢复与重试。
6. 记忆能够影响路径选择和默认偏好，失败也能降低经验可信度。
7. 按部署文档可在新环境启动、持久化、运行调度、重启恢复和回滚。
8. 明确区分代码缺陷、应用状态异常、外部依赖故障与证据不足。

## 2. 当前事实与待确认范围

### 2.1 可以复用的基础

现有项目已实现并有部分测试覆盖：

- ADB TCP 设备操作、应用启动、按键、输入、截图和 UI XML 解析。
- 飞牛 TV 按页面导航、常用指令快速路径、原 YAML Flow。
- ScreenState、结果分级核验、任务状态、跨进程设备锁、暂停和取消。
- 分类恢复器、模型 JSON 工具循环、15 个 MCP 工具及参数校验。
- SQLite 任务历史、经验路径、页面特征、恢复统计、偏好和候选 Skills。
- Skills 隔离验证与人工审批接口。
- HTTP 控制台、异步任务、SSE、模型设置、调度与 Docker 配置文件。

以上说明“有实现”，不表示所有模块组合与真实使用路径已经正确。

### 2.2 已确认需要修复的问题

| 编号 | 问题 | 实际影响 |
|---|---|---|
| W01 | 首页 HTML 在展示登录表单前要求认证头 | 普通浏览器首次访问得到 401 |
| W02 | SSE 使用包含查询参数的完整路径判断后缀 | 浏览器的正确令牌请求仍可能被拒绝 |
| W03 | 模型配置保存调用不存在的 os.mkstemp | 合法配置保存返回 500 |
| E01 | 已释放的历史 AudioTrack 未排除 | 已停止的视频可能仍被认为在播 |
| E02 | 指定内容已确认后，音频和播放器证据未正确组合 | 飞牛实际播对仍可能一直 PARTIAL |
| E03 | 通用暂停/继续使用飞牛的 CENTER 规则 | 其他应用或非播放器页面可能被误点击 |
| E04 | 简单目标前后都进行全量 fresh 感知 | “打开飞牛”在隔离计数中仍有15次设备读取 |
| E05 | 复合指令、查询和部分常用动作解析不完整 | 要求被丢弃，或任务被错误分类 |
| E06 | 失败结果未统一进入恢复，retry 未实际重执行 | 有恢复记录但没有形成恢复闭环 |
| E07 | 返回首页、返回、音量等缺少语义核验 | 已执行的操作仍被记为 UNKNOWN |
| L01 | 路径失败没有完整反馈至经验可靠度 | 学习统计偏向成功，不能识别退化路径 |
| R01 | HTTP 任务每次创建线程且缺少队列上限 | 长期运行存在无界积压和资源保留 |
| D01 | Docker 缺依赖、状态路径与只读配置不一致 | 按文档部署可能无法启动 |
| D02 | 只启动 serve，未启动调度执行器 | 网页新增调度任务可能一直不执行 |
| D03 | Skill 模拟验证依赖源码树 tests/fake_adb.py | 正常安装包或镜像可能缺失验证能力 |

主要涉及现有 agent、device、perception、verifier、recovery、skill_engine、server、config、execution 和部署文件。应优先修复与接通现有实现。

### 2.3 不应继续直接采用的结论

- 不能只凭飞牛骨架屏持续存在就认定“NAS 后端故障且与代码无关”；还需检查网络、服务可达性、登录状态、接口错误和应用自身状态。
- 不能把早期快速路径的耗时当作当前完整 managed + Skills 路径的速度保证。
- 不能把客户端自动附加认证头的 HTTP 测试，当作普通浏览器完整登录/SSE 验收。
- 不能把模拟设备成功率当作真机成功率。
- 当前回归存在一个使用约50毫秒真实时间预算的时间敏感用例；需消除测试偶发性，而非简单把失败忽略。

## 3. 优先级和实施边界

| 优先级 | 范围 | 完成要求 |
|---|---|---|
| P0 | 登录、SSE、配置保存、播放误判、目标弱化、部署阻断 | 在进一步扩展功能前修复 |
| P1 | 常用动作、按目标感知、恢复闭环、任务队列、结果反馈 | 达到日常可用和可衡量的性能目标 |
| P2 | 媒体索引、直接定位、多轮上下文、经验闭环、运维诊断 | 在P0/P1稳定后逐步交付 |
| P3 | 完整语音、跨应用推荐、多设备和主动服务 | 独立立项，不影响核心任务稳定性 |

兼容边界：保留原 CLI、15 个 MCP 工具名称、现有 HTTP 接口和 YAML Flow。确需变更的返回字段与配置必须提供迁移说明；新增能力优先通过可选字段或明确版本接口提供。

## 4. P0：修复真实使用入口

### 4.1 控制台登录和认证

目标：浏览器无需预先拥有自定义请求头，就能看到登录页面；登录后才可读取设备和执行操作。

要求：

- 登录页和必要静态资源可匿名读取，设备、任务、截图、配置和记忆接口继续强制认证。
- 凭证存储与会话方式统一设计；优先使用合适的安全会话，或通过带认证头的流式请求读取进度。
- 不将长期有效的控制令牌放在可被历史、代理日志或错误报告持久记录的 URL 中。
- 首页重载、退出、凭证失效和多标签页行为有明确结果。

验收：在全新浏览器会话中完成“打开页面 → 登录 → 查看设备 → 提交任务 → 退出”；退出后控制接口必须被拒绝。不能用测试客户端默认认证头绕过这个过程。

### 4.2 实时进度和任务反馈

目标：真实浏览器可持续看到执行事件与最终结果。

要求：

- 路径解析和查询参数解析分离，SSE 认证方式与前端实际请求一致。
- 支持断线重连或手动恢复，并避免重复显示事件。
- 不存在的任务返回明确错误，不长时间占用连接。
- 正常结束、取消、暂停和失败都有终态或可恢复状态。
- 进度明确区分排队、连接设备、等待页面、查找内容、执行、核验、恢复和人工接管。

验收：浏览器实际 EventSource 或流式 fetch 不带隐含测试认证头也能按设计工作；服务器记录与页面结果一致；任务结束后连接和线程被回收。

### 4.3 模型配置与凭证

目标：模型配置可以保存、重新加载和应用于新任务，不影响正在执行的任务。

要求：

- 修复临时文件创建，使用原子写入与受保护权限。
- 配置更新与新任务构造串行或按快照处理；正在执行的任务使用自己的配置快照。
- 保留其他配置段和用户别名，不把配置管理变成任意文件写入。
- 配置 API、CLI 诊断和日志统一遮蔽模型 Key、控制令牌等凭证。
- 明确无配置文件时的创建位置，不能依赖源码目录可写。
- 本机网关忽略 system 字段的兼容行为应可配置，不影响正常云端接口。

验收：保存合法配置成功，重启后仍存在；非法值不改原文件；凭证不出现在返回值、日志和记忆中；并发任务不读取到一半更新的配置。

## 5. P0/P1：完整理解并保留用户目标

### 5.1 统一目标结构

目标：快速路径、Skills 和模型规划共用同一个不可静默弱化的目标结构。

建议字段：

- 任务类型：查询、打开、搜索、播放、遥控、定时或多步骤。
- 应用、媒体库、片名、别名、季、集。
- 操作列表及顺序。
- 搜索与播放的区别。
- 时间约束：等待多久、何时执行、播放多久后暂停。
- 播放策略：续播、从头、下一集、指定进度。
- 明确成功条件和不支持的条件。

示例：

```json
{
  "steps": [
    {"action": "play", "app": "feiniu", "title": "穿成野神我靠香火斩诸神", "season": 1, "episode": 1},
    {"action": "volume_change", "delta": 1},
    {"action": "pause_after", "seconds": 600}
  ],
  "completion_policy": "all_required_steps"
}
```

实现不必照搬字段名称，但必须保留同等语义。若某项未支持，应明确告知，而不是只播放就报告整条指令成功。

### 5.2 第一批必须支持的指令

| 类型 | 示例 | 预期行为 |
|---|---|---|
| 查询 | 现在播放的是什么？当前在哪个应用？ | 只读查询，不触发播放 |
| 打开 | 打开飞牛 / 打开B站 | 核验前台应用 |
| 搜索 | 在飞牛搜索野神，不要播放 | 进入并展示结果，不擅自选播 |
| 播放 | 播放野神第一部第一集 | 保留片名、季集并核验 |
| 续播 | 继续刚才那部 / 从头播放 | 明确续播或从头，不混淆 |
| 选集 | 下一集 / 上一集 / 第十集 | 识别当前剧并切换对应集数 |
| 进度 | 快进30秒 / 后退10秒 / 跳到第5分钟 | 按应用能力执行并核验 |
| 遥控 | 暂停、继续、返回、回首页、音量加减 | 使用当前应用适配规则 |
| 复合 | 播放X，然后调大一点声音 | 所有必需步骤均被执行或明确报告未完成 |
| 延迟 | 十分钟后暂停 | 建立可查询、可取消的延迟任务，不立即暂停 |

验收包含口语、书名号、中英文数字、简称、否定条件以及同一句话不同顺序。“找个《明确片名》”不能因“找个”清空片名。

## 6. P0/P1：播放状态与内容身份核验

### 6.1 播放状态

目标：区分正在播放、暂停、停止、缓冲、结束和证据不足。

要求：

- 区分当前活动音轨与历史事件，释放的 AudioTrack 不得继续作为 started 证据。
- 关联目标包、进程与当前播放器，避免其他应用、旧进程和旧会话污染结果。
- MediaSession、音轨、播放器页面、UI 控件和实际进度分别记录来源、新鲜度与冲突。
- 未获取播放状态不等于“已经暂停”，也不等于“播放失败”。
- 广告或预览不能独立证明用户指定的正片已开始。

验收必须覆盖：播放→暂停→继续→结束→退回详情、进程重启、旧音轨释放、新音轨创建、多应用后台会话、无声视频和无 MediaSession 的飞牛播放器。

### 6.2 内容身份与播放证据合并

目标：避免假成功，同时减少内容正确时的假阴性。

要求：

- 音频不能证明片名；但片名与季集已由当前播放器独立确认后，允许结合目标播放器及其活动音轨判断播放。
- 指定身份未知时只能 PARTIAL/UNKNOWN，不依靠模型描述补证。
- 不要求同一条件由每种证据重复证明；按目标组合有效证据。
- 仅要求进度推进时才做额外采样，且数值必须来自真实设备状态。
- 不把已执行且无法确认的结果与明确失败混为一谈。

验收案例：当前飞牛 PlayerActivity 的 XML 明确出现正确片名和 S01E001，目标应用音轨活动、无 MediaSession；该组合应能满足对应的内容与播放条件。错误标题、错误集数、历史音轨和详情页标题仍不得通过。

### 6.3 基本遥控核验

- home：核验系统实际 HOME 应用或桌面状态。
- back：比较导航前后页面、层级或弹窗状态，明确区分返回与隐藏控制栏。
- volume：读取目标音量流的前后值，边界值时反馈“已达最大/最小”。
- pause/resume：按应用能力选择幂等操作；CENTER 切换仅用于已确认适用的播放器。

未知状态先观察；不得在应用首页盲按 CENTER。记忆开关不应改变暂停/继续的设备控制语义。

## 7. P1：按目标感知与性能优化

### 7.1 观察分级

| 任务 | 默认采证 | 升级条件 |
|---|---|---|
| 打开应用 | 前台包与Activity | 启动异常才读取XML |
| 暂停/继续 | 播放器与媒体/音频状态 | 无法确定控制态时读取UI |
| 返回/音量 | 页面状态或目标音量流 | 结果不明确再补充读取 |
| 指定内容/选集 | 一份完整UI快照及必要系统状态 | XML不足时才视觉 |
| 复杂任务 | 与下一动作相关的观察 | 不能每步无差别发送整张截图 |

要求：

- 一次观察复用窗口、媒体会话和XML结果，避免同样数据重复读取。
- 每条任务共享短期快照；动作、前台变化和主动刷新使相应缓存失效。
- XML和截图按需获取；播放器进度文字变化不能让所有结构缓存失效。
- 记录完整 managed 路径耗时，而非仅内层快速路径耗时。
- 模型调用数、ADB读取数、UI dump数、等待时间和核验时间可统计。

### 7.2 性能验收目标

以下为建议目标，不是当前实测保证。先建立稳定基线，再根据电视能力校准。

| 场景 | 建议目标 |
|---|---|
| 目标应用已在前台的“打开应用” | 不调用模型，不做UI dump，设备读取不超过2次 |
| 常用暂停/继续 | 不调用模型，证据充分时不做UI dump，设备查询不超过6次 |
| 无外部慢依赖的基础遥控 | 实机重复测试 P95 尽量不超过2秒 |
| 飞牛首页播放任意短剧 | 无强制5+4+4秒等待；同条件P95相对当前基线下降至少30% |
| 指定片名/季集 | 单独报告检索、页面导航和核验耗时，不用“任意短剧”速度代替 |
| 外部服务长期无响应 | 在明确预算内停止；不能不断重启应用、重复点击或再进入完整LLM超时 |

测量范围包括解析、排队、连接、观察、执行、核验、落库与反馈；分别统计中位数、P95和失败样本。网络/模型耗时单独列出，但不得从总体验耗时中隐去。

## 8. P1：有界恢复与人工接管

目标：将恢复器真正接入任务执行结果，而非仅保留独立模块。

要求：

1. 返回 ok:false、异常、页面无变化、验证不通过都进入统一失败分类。
2. 根据原因执行不同恢复：重连、重观察、安全关闭弹窗、返回、重新定位、重新启动目标应用。
3. retry:true 后必须真的重试对应步骤，或重新制定计划；记录重试前后的效果。
4. 只重试失败步骤，不盲目从头重复已成功或有副作用的操作。
5. 保留完整用户目标，恢复不能改播其他内容来满足“有声音”。
6. 限制单类重试、总恢复、动作次数和总预算，超限明确交人工。
7. 用户取消优先于恢复；被取消的任务不得由调度或恢复器意外重启。
8. 人工遥控冲突检查覆盖快速路径、内置Skills、审批Skills和模型路径，不能只在模型循环中存在。

暂停策略必须明确：区分自动执行预算、人工暂停时长与排队期限；不能让用户接管几分钟后发现任务被不明原因消耗完。对自动页面跳转、滚动和视频变化设置合理容忍，避免误判人工接管。

验收：模拟断线、一次点击无变化、遮挡弹窗、临时搜索失败、短时缓冲和人工切换焦点，证明恢复确实发生；同时证明同类错误不会无限循环。

## 9. P1：长期运行与调度可靠性

### 9.1 统一任务执行器

- 使用有界队列与固定工作线程，设置最大排队数和等待期限。
- 队列满时返回明确状态，不继续创建无限线程和任务文件。
- 完成任务及时回收 Future/线程引用与SSE连接。
- 服务重启识别遗留 RUNNING/QUEUED，不无限显示运行中，不自动重放结果不明的高风险操作。
- CLI、HTTP、MCP与调度共用设备互斥规则和状态表示。

### 9.2 调度必须实际运行

- 控制台不仅能添加任务，还能看到执行器是否在线、下次运行时间和失败原因。
- 交付明确的独立调度服务或受控后台执行器；Docker和systemd部署均能同时运行控制台与调度。
- 支持启用、停用、修改、删除和可查询的延迟任务。
- 保留现有JSON兼容、原子领取、时区与有限重试；明确崩溃窗口不保证副作用exactly-once。

### 9.3 数据与维护

- 普通 clean 只清可重建缓存，不删除任务历史、当前控制文件、数据库、令牌和锁文件。
- 数据保留与清理由独立命令管理，先预览、可备份，且不干扰活跃任务。
- 日志轮转、任务历史分页与数据库清理可配置；历史查询不能每次遍历所有文件后才截取100条。
- 运行数据统一进入配置的数据目录，源码目录可只读。

## 10. P1/P2：记忆、偏好与 Skills 形成闭环

### 10.1 经验有效性

- 每条执行路径记录成功、失败、耗时、版本、起始页面和适用条件。
- 失败必须降低可靠度；连续退化路径能被停用或要求重新验证。
- 恢复方法的成功依据为该次恢复是否解决原错误，不是整条任务最终成功与否。
- 比较候选路径时同时考虑成功率、样本量、时间和适用页面，而非只记成功次数。
- 用户明确设置的默认应用、续播偏好等应实际进入目标解析；不从敏感数据擅自推断偏好。

### 10.2 Skill 可用性与审批

- 审批界面可查看完整步骤、适用应用、前置条件、成功条件、验证报告和变更差异，不能只显示名称和批准按钮。
- 候选Skill的文字输入被脱敏后，不能把脱敏标记作为生产搜索词执行；应使用受控参数模板，明确哪些参数由用户本次任务提供。
- 验证结果关联定义哈希；定义改变后，旧验证和批准必须失效。
- 正常安装包与镜像包含专用模拟器/验证资源，不能依赖未打包的 tests 目录。
- 隔离模拟验证与生产兼容性分开表示，不能把“模拟通过”描述为“任何电视可用”。
- 对恢复策略、max_retries、success等Skill字段，要么真实执行并验证，要么拒绝未实现字段，不能接受后无效。

## 11. P0/P1：部署、迁移和回滚

目标：按文档在干净环境完成安装，不依赖开发者主目录的隐含状态。

要求：

- Docker实际安装PyYAML等声明依赖；测试干净镜像，不借用宿主机已安装包。
- 配置、数据库、任务、日志、令牌、ADB密钥使用明确且可写的持久目录。
- UID/GID、目录属主和权限与容器用户一致；只读根目录下正常运行。
- 控制台和调度均有明确启动方式、健康状态和停止方式。
- 端口被占用时明确诊断，不替换或终止无关进程。
- 提供从现有config到新配置的迁移、数据备份与恢复说明。
- 发布包、wheel和Docker镜像包含UI、内置能力、验证资源及必要文档。
- 快照名称、项目版本与文档记录一致；每个实际验收过的阶段都有可恢复版本。
- 不直接覆盖用户未提交文件或私人配置；配置模板默认不包含真实凭证。

验收：从干净安装启动 → 登录 → 发任务 → 新增到期调度并执行 → 写入记忆 → 重启后保留 → 备份 → 恢复。Docker未实际构建运行时只能标“待容器验收”。

## 12. P2：最有价值的发展方向

### 12.1 飞牛媒体库索引与直接定位

优先核实合法、稳定且可认证的媒体检索和播放入口；无可用接口时继续保留ADB适配。

能力目标：

- 索引片名、别名、媒体ID、季集、可用文件与最近观看位置。
- “野神第一部”“继续上次那部”可解析到明确的媒体实体。
- 优先精确搜索和直接定位，避免逐页翻卡片。
- 片名重名或季号含糊时给候选，不能随意选择。
- 索引失效时可刷新或回退ADB，不把缓存当真实播放结果。

是否采用接口或Deep Link，以实际核实结果决定，不预先承诺某个飞牛版本一定支持。

### 12.2 多轮对话与会话上下文

- 支持“换第二部”“从第一集开始”“下一集”“还是刚才那部”。
- 将当前剧、集数、候选列表、用户指代与会话绑定。
- 区分临时上下文与长期偏好；不同用户/会话不串内容。
- 有歧义时简短确认，不默认改播。

### 12.3 面向手机的快捷控制

- 登录后直接看到当前应用、片名、季集、播放态和主要操作按钮。
- 提供最近观看、继续播放和最近指令。
- 用中文解释“已操作但待确认”“正在等媒体库”“恢复一次仍失败”。
- 移动端浏览器实际验证，截图刷新和任务进度不互相抢设备锁。

### 12.4 应用能力适配层

为飞牛、B站、红果和通用Android TV建立能力声明：是否支持搜索、选集、进度、倍速、字幕、媒体键、播放器控件和UI文字识别。优先完善飞牛，再按实际需求适配其他应用。

每个应用维护少量有版本信息的页面样本与回归任务，更新后能判断是适配退化还是设备/服务异常。

### 12.5 诊断与可观测性

- 设备在线、ADB授权、模型可达、媒体服务状态分别展示。
- 任务显示分阶段耗时、真实执行次数和未满足的成功条件。
- 自动生成脱敏诊断包，不导出Key、令牌和原始敏感UI。
- 提供历史对比，证明优化确实降低延迟或失败率。

## 13. 暂缓事项

在核心可用性和验收完成前，暂缓：

- 多设备协同、大规模主动推荐、无人监督的主动播放。
- 永久在线麦克风、唤醒词、本地ASR/TTS整套部署。
- 复杂前端框架迁移、分布式队列、额外数据库服务。
- AI自动生成并执行生产源码、未经审批自动启用新Skill。

现有网页语音入口保留为可选。后续语音应以手机/电脑浏览器麦克风或明确配置的采集端为来源，不能假设NAS能读取小米遥控器麦克风。

## 14. 测试与验收要求

### 14.1 三层验证

1. 模块测试：解析、证据、参数、存储、恢复、队列等。
2. 完整入口测试：真实Agent.run的managed + Skills路径、HTTP无隐含认证头、安装包路径、真实调度执行器。
3. 真机与浏览器验收：应用版本、起始页面、环境与实际结果完整记录。

测试必须覆盖失败、取消、超时、证据不足与重复执行，不能只覆盖演示成功流程。

### 14.2 消除测试盲区

- 不用缺少adb属性的内存对象代表完整Agent入口的性能。
- 浏览器测试首次访问不能自动加认证头；SSE请求须与浏览器实际方式一致。
- 模型配置保存须实际写入临时配置、重读并校验，不只mock返回成功。
- 使用可控时钟或合理预算验证超时，不用50毫秒真实墙钟制造偶发失败。
- 关键“恢复器 + Agent”“内容核验 + 播放核验”“记忆 + 路径选择”必须组合测试。
- Docker、wheel安装后的资源定位须单独测试。

### 14.3 建议30项重复验收清单

每项运行3次；记录原始结果，不隐去重试和失败。先在模拟环境重复，再按可用设备进行真机验收，二者分表。

- 不允许漏掉必需步骤却报告整条任务成功。

## 15. 建议交付顺序

### 里程碑一：真实可用修复版

修复登录/SSE/配置保存、目标弱化、播放误判、容器阻断；补完整入口回归。交付可从浏览器和CLI真实完成的基础版本。

### 里程碑二：快速稳定的飞牛助手

完成分级感知、遥控与选集、真正的有界恢复、任务队列、调度执行器和友好反馈；建立P95与重复任务基线。

### 里程碑三：媒体定位与经验优化

核实媒体接口、建设索引与会话上下文；打通偏好、成功失败统计和路径选择，完善Skills审批与安装资源。

### 里程碑四：交互扩展

核心指标稳定后，再扩展其他应用、语音、手机快捷入口和多设备支持。根据实际需求确定范围，不将它们设为基础稳定性的前置条件。

## 16. 每阶段完成标准

每阶段交付必须包含：

1. 实际修改代码、变更清单和兼容性说明。
2. 实际执行的测试命令、结果和失败样本。
3. 可复现的性能记录与起始条件。
4. 真机/浏览器/容器验收表，未运行项明确标注。
5. 更新的配置样例、部署迁移和回滚说明。
6. 可恢复的版本快照及其校验值。
7. 未解决问题和下一阶段边界。

本优化任务完成的判断标准是：用户能稳定完成常用操作，系统能解释并保留全部目标、清楚说明实际结果，执行速度和可靠性有真实数据支撑，而不是仅有相关模块、接口和通过数量。
